# 01 — 代码优化（Code Optimization）

## 何时触发

- 用户说"优化这段代码"、"重构"、"性能有问题"
- 发现代码异味：长函数、重复代码、深层嵌套、God Class
- 代码审查中发现需要改进的部分
- 新功能开发前需要清理现有代码

## 核心准则

### 1. 先诊断，后治疗

**永远不要在理解问题之前动手修改。**

```
诊断阶段：
├── 1. 阅读相关代码（至少上下游 2 层调用）
├── 2. 识别具体问题（仅列出，不急于修）
├── 3. 评估影响范围（哪些模块/测试会被影响）
├── 4. 确定优先级（先修影响最大的）
└── 5. 制定优化计划（告知用户，等待确认）
```

### 2. 最小化修改原则（Karpathy Rule #3）

```
✅ 只修改有问题的部分
✅ 保持现有接口不变（除非接口本身就是问题）
✅ 匹配项目现有代码风格
❌ 不要"顺路优化"无关代码
❌ 不要引入新的依赖
❌ 不要重写整个模块除非明确要求
```

### 3. 代码异味检测清单

| 异味类型 | 检测标准 | 处理策略 |
|----------|----------|----------|
| **长函数** | >30 行（非配置类） | 提取子函数，单一职责 |
| **重复代码** | 相同逻辑出现 ≥2 次 | 提取公共函数/工具类 |
| **深层嵌套** | if/for 嵌套 >3 层 | 提前 return / 提取条件判断 |
| **God Class** | 单文件 >300 行 或 >10 个公共方法 | 按职责拆分 |
| **魔法数字** | 未命名的字面量 | 提取为命名常量 |
| **过多参数** | 函数参数 >4 个 | 使用参数对象/配置模式 |
| **注释过多** | 注释行 > 代码行 | 用清晰命名替代注释 |
| **死代码** | 从未被调用的代码 | 删除（Git 历史可恢复） |
| **硬编码** | 环境/配置硬编码 | 提取为配置/环境变量 |

### 4. 性能优化检查清单

```
□ 是否进行了基准测试？（优化前必须知道当前性能）
□ 瓶颈是否在预期位置？（不要凭直觉优化）
□ 优化后是否重新测试？（验证改进效果）
□ 是否引入了新的复杂度？（复杂度换性能需要明确理由）
□ 是否考虑了缓存策略？
□ 是否减少了不必要的重渲染/重计算？
```

## 工作流程

### 阶段一：理解（Understand）
1. 阅读目标代码及上下游
2. 运行现有测试确保理解正确
3. 记录当前行为作为基线

### 阶段二：计划（Plan）
1. 列出所有发现的问题
2. 评估每个问题的优化收益与风险
3. 按风险从低到高排列优先级
4. 向用户呈现计划并等待确认

### 阶段三：执行（Execute）
1. 按计划逐项修改
2. 每项修改后运行相关测试
3. 保持每次 commit 原子化（一个问题 = 一个 commit）

### 阶段四：验证（Verify）
1. 运行完整测试套件
2. 对比优化前后的性能指标
3. 检查是否引入新的 lint 警告
4. 更新相关文档

## 禁止事项

- ❌ 在未理解代码意图的情况下重构
- ❌ 删除看似"无用"但可能有副作用的代码
- ❌ 改变函数签名而不更新所有调用方
- ❌ 将简单问题复杂化（过度设计）
- ❌ 优化非瓶颈代码（过早优化是万恶之源）
