# 02 — 规则化管理（Rule Management）

## 核心理念

> 规则是 AI 的行为契约。没有显式规则，AI 会自由发挥；规则混乱，AI 会行为分裂。

## 规则三层体系

```
┌─────────────────────────────────┐
│       团队级规则 (Team)          │  ← 所有项目共享（代码风格、安全规范）
│   .codebuddy/team-rules/        │
├─────────────────────────────────┤
│       项目级规则 (Project)       │  ← 当前项目专用（架构约束、技术选型）
│   .codebuddy/CLAUDE.md          │
│   .codebuddy/rules/             │
├─────────────────────────────────┤
│       用户级规则 (User)          │  ← 个人偏好（语言、工具链偏好）
│   ~/.codebuddy/CLAUDE.md        │
└─────────────────────────────────┘
```

**优先级**：项目级 > 用户级 > 团队级（越具体优先级越高）

## 规则生命周期

```
创建 → 审查 → 发布 → 激活 → 更新 → 废弃
  │      │      │      │      │      │
  ▼      ▼      ▼      ▼      ▼      ▼
 模板   团队   版本号  自动   变更   archive
        Review  v1.0  加载   日志   目录
```

### 创建规则模板

```markdown
---
rule_id: RULE-XXX
version: 1.0.0
priority: high | medium | low
scope: project | user | team
applies_to: always | manual | pattern
patterns: ["*.ts", "*.tsx"]
conflicts_with: []
supersedes: []
---

# 规则名称

## 目的
简明说明此规则解决什么问题

## 适用场景
何时触发此规则

## 行为约束
1. 必须执行...
2. 禁止...
3. 建议...

## 例外情况
何时可以违反此规则

## 示例
✅ 正确做法
❌ 错误做法
```

### 版本控制

```
v1.0.0 → v1.1.0 → v2.0.0
  │         │         │
 发布     新增功能   破坏性变更
          (向后兼容)  (需要迁移)
```

### 优先级仲裁

当多个规则冲突时，按以下顺序仲裁：

1. **scope** 更具体的规则优先（project > user > team）
2. **priority** 更高的规则覆盖（high > medium > low）
3. **version** 更新的规则覆盖（v2 > v1）
4. 如果以上均无法仲裁 → 暂停并向用户询问

## 规则管理命令

### 创建规则
```
使用 02-rule-management 技能时，AI 应：
1. 询问规则目的和范围
2. 检查是否与现有规则冲突
3. 使用模板生成规则文件
4. 分配 rule_id 和版本号
5. 写入对应目录
```

### 审查规则
```
1. 列出所有活跃规则
2. 检查过期规则（超过 90 天未更新）
3. 检测冲突规则对
4. 建议废弃/合并/更新
```

### 导出规则
```
1. 收集指定范围的规则
2. 生成 markdown 合集
3. 可选：生成 JSON/YAML 格式
```

## 最佳实践

| 实践 | 说明 |
|------|------|
| **规则要有理由** | 每项规则必须解释"为什么"，不只是"做什么" |
| **规则要可验证** | 规则是否被遵守应该是可检查的 |
| **规则数量限制** | 项目级规则不超过 10 条（太多规则等于没规则）|
| **定期审查** | 每月检查一次规则是否仍然适用 |
| **变更记录** | 每次修改规则要记录原因和时间 |
