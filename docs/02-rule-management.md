# 02 — 规则管理 详细文档

> 对应技能：`.codebuddy/skills/02-rule-management/SKILL.md`

## 为什么需要规则化？

AI 编程助手的行为依赖于规则。没有显式规则：
- AI 每次的行为都不一致
- 团队成员体验到的 AI 行为不同
- 新人需要口头传授"怎么跟 AI 说话"

有了规则体系：
- AI 行为一致、可预测
- 团队共享同一套约束
- 规则可以版本化、审查、演进

## 规则体系架构

```
┌─────────────────────────────────────────────┐
│ 团队规则 (~/.codebuddy/team-rules/)         │
│ 所有项目的通用约束                            │
│ 例如：安全规范、代码风格、提交规范              │
├─────────────────────────────────────────────┤
│ 项目规则 (.codebuddy/CLAUDE.md + rules/)    │
│ 当前项目的特定约束                            │
│ 例如：架构决策、技术选型、目录规范              │
├─────────────────────────────────────────────┤
│ 用户规则 (~/.codebuddy/CLAUDE.md)           │
│ 个人偏好和工作习惯                            │
│ 例如：语言偏好、工具选择                       │
└─────────────────────────────────────────────┘
```

## 规则编写指南

### 好规则的特征

✅ **具体可执行**："所有 API 路由文件必须以 `.route.ts` 结尾"
❌ **模糊笼统**："代码要规范"（太模糊，无法执行）

✅ **解释原因**："禁止使用 `any` 类型，因为会失去类型安全"
❌ **只有命令**："不要用 any"（没说为什么）

✅ **可验证**："每个公共函数必须有 JSDoc 注释"
❌ **主观判断**："代码要好看"（怎么算好看？）

### 规则数量控制

| 规则数量 | 效果 |
|---------|------|
| 1-5 条 | 清晰易记 |
| 6-10 条 | 可管理，需要文档 |
| 11-20 条 | 开始有负担，需要优先级 |
| 20+ 条 | 太多规则等于没规则 |

**建议**：项目级规则不超过 10 条，超过的需要拆分或合并。

## 规则冲突处理实例

```
场景：两条规则冲突

规则 A（用户级，优先级 high）：
  "所有新建文件使用 TypeScript"

规则 B（项目级，优先级 medium）：
  "配置文件使用 JavaScript（兼容工具链）"

仲裁结果：规则 B 生效
  原因：规则 B 的 scope 更具体（project > user）
```

## 规则的维护

```
每月一次规则审查：
├── 检查每条规则的触发频率
├── 标记超过 30 天未触发的规则为"待审查"
├── 合并表达相同意图的多条规则
├── 废弃不再适用的规则
└── 更新版本号
```
